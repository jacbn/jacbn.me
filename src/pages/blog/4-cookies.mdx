# Cookies!

While I've always been comfortable with what the *idea* of a cookie is – a piece of data sent by a server to a browser – it seems that, once a project has decided on policies defining the site's cookies, these policies rarely change and are thus rarely subject to scrutiny. This makes cookies a rather difficult topic to learn about "while doing"... which is unfortunately how I best learn.

This blog post, therefore, is a personal attempt to rectify any missing knowledge, while also serving as a useful foundation to anyone – or, more likely, the 2000+ bots that scrape my site daily – in the same situation.

## Purpose

### Session management

Suppose a site requires that you be logged in to access certain information. You log in, access what you need, then attempt to navigate to another section of the site that would also require the same authentication. 

It would be a rather terrible user experience if you had to log in *again*, and indeed once for every new page that required authentication. To avoid this, we can make use of an **authentication cookie**.

On the first successful login, when the server responds with information that the process was successful, a cookie is attached to the response containing a session ID. This cookie represents the *browser's* understanding of whether the user is signed in; it will be attached to all future requests requiring authentication. These future requests will have the cookie be checked by the server and, if still valid, acts as authentication without requiring the user to sign in again. This works because, under the assumption of a secure connection, only the browser and server know this cookie; the server can be certain that the incoming requests were made by the same user, and so long as the session is still valid, this user remains authenticated.

These cookies have other benefits too. Since the cookie's session ID is unique to a user, it can act as a key to a database on the server storing information about that session. Such information might include, for example, the state of the cart of a user shopping online, so that the session is only lost when the cookie is. This enables "guest shopping", where a user doesn't need to be logged in to make use of a cart. Note that for shopping there is no need for authentication, so session IDs can be generated immediately for all users, rather than only on successful sign in; this enables e.g. guest shopping functionality.

> The contents of the shopping cart could indeed be stored *inside* the cookie, and that this was the norm many years ago. However, for ease of integrating this with accounts and for better tracking and recommendation purposes, the norm has shifted towards storing the cart contents in the backend, using the session ID to request this info.

### Personalisation

Many personalisation options provided on the modern web require you to be logged in to function, owing simply to these user options being tied to a user ID in a database. However, by setting a long-life persistent cookie, it becomes possible to modify requests to a server with personalisation information; this could be used to limit the number of items displayed on a listing, or the colour theme if HTML is being generated on the server.

This practice is unfortunately dying out as companies have realised the value in signing users up to a service – locking non-essential features behind an account increases the likelihood of users doing this.

### Tracking

Using the same method as session management, cookies can be used to track how users navigate around a site. Each request made to a server would include the tracking cookie; if the cookie is not present, then it can be assumed that this was the first page load and a new cookie is generated by the server for this user.

If the cookie is present, then the page view can be added to a list of page views stored by that session ID. If they log in after viewing certain pages, these views can then be tied to the user ID. Each view might store e.g. a timestamp and a duration of activity. While this information can be used for good – e.g., understanding which pages in a flow take the longest to navigate through, and thus can be assumed to have the most friction – these are nowadays almost exclusively used to exploit a user's habits. Understanding which pages capture the user's attention for the longest assist with targeted advertising, for example. This information is highly lucrative, especially so for commercial websites – and so even if it is not being used directly, it is likely being collected to be sold off to advertising companies.

## Technical implementation

With a comprehensive idea of how cookies are used, understanding how they are implemented is next.

### Creation

A server can inform a browser to create a cookie by defining a value inside the `Set-Cookie` header field of an HTTP response. For example, if a browser makes a GET request for the `index.html` file:
<div className="d-flex w-100">
```
GET /index.html HTTP/1.1
Host: www.example.org
...
```
</div>
A server, wishing to send two cookies (one personalisation cookie, one authentication cookie), may respond with:
<div className="d-flex w-100">
```
HTTP/1.0 200 OK
Content-type: text/html
Set-Cookie: theme=light
Set-Cookie: sessionToken=abc123; Expires=Wed, 25 Dec 2026 12:18:14 GMT
...
```
</div>
The contents of a cookie is the first part, immediately after `Set-Cookie:`. After this, a semicolon separates the contents from the **attributes**. The attributes are used by browsers to determine when to delete or send a cookie to the server. Note that the attributes are never sent back to the server.

#### Attributes

- `Domain` specifies the web domain (or specific subdomain) that the cookie will be set on. A cookie can only be set on a given resource's top domain and subdomains (i.e., a cookie for `example.org` may only set cookies on `example.org` or e.g. `sub1.example.org`), for security reasons. If the domain is set, requests from all subdomains will include the cookie. If the domain is omitted, only requests from that specific domain will include the cookie – a *host-only* cookie.
- `Path` specifies a path to a given resource, for which all requests made to that path (or a more specific path) will use the cookie.
- `Expires` defines a date and time for when the browser should delete the cookie. They take the form `Wdy, DD Mon YYYY HH:MM:SS GMT`, but can use a 2-digit year `YY` if `0 <= YY <= 69`. An expiry date set in the past will immediately delete the cookie.
- `Max-Age` is an alternative deletion marker, specifying a number of seconds from creation after which the cookie should be deleted. Note that if neither `Expires` nor `Max-Age` is specified, it will be deleted when the user closes their browser (a *session cookie*).
- `Secure` is a value-less attribute whose presence indicates a cookie that should only be used on secure connections (HTTPS). This does not make the cookie secure in any meaningful way, only indicating that it is sensitive. Note that `http://localhost` is an exception to this rule on all browsers **except on Safari**.
- `HttpOnly` is a similarly value-less attribute whose presence directs a browser not to expose cookies through means other than HTTP / HTTPS. This prevents e.g. JS stealing cookies in XSS attacks.
- `SameSite` specifies whether the cookie should be sent with *cross-site requests* (that is, requests to third-party sites from embedded content, and requests sent when a link is clicked on another site that navigates to the cookie's origin site). This attribute can take the values of:
  - `Strict`, causing the browser to only send the cookie on requests matching the origin site (not sent to third parties);
  - `Lax`, which also sends the cookie if the user navigates to the cookie's origin site;
  - `None`, which always sends the cookie, including to all third parties.

Cookies are treated as `Lax` if no `SameSite` value is set. `Strict` is required for authentication- or account-related information which must not leak, and `None` for information pertinent to e.g. analytics or advertising services. `Lax` has the benefit of allowing other sites to indicate that they were the one that sent you, making it particularly useful for affiliate information.

### Updating and Deleting

If the server "sets" a new cookies with the same name, path and domain, the existing cookie will be updated. Given that cookies are deleted if their `Expires` date is in the past or if their `Max-Age` reaches 0, setting either of these will delete the cookie. All cookies for a site (incl. subdomains) can be deleted using another HTTP response header, `Clear-Site-Data: "cookies"`. 

JavaScript can also access non-`HttpOnly` cookies via [`document.cookie`](https://developer.mozilla.org/en-US/docs/Web/API/Document/cookie).
